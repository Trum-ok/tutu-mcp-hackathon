# Замеры и находки

Дополнение к [README](../README.md): сырые цифры и мотивирующий кейс, на которые опираются
решения в коде. Замеры сделаны вручную 19.08.2026 по живому серверу `tutu-mcp-server` версии
`0.38.0` (`https://mcp.tutu.ru/mcp`), сырые ответы лежат в `fixtures/`.

## Кейс: выдуманная предпосылка

Запрос: «поездка одним днём в Питер на концерт 11 октября, что выгоднее по транспорту».

Без премис-гейта ассистент строит полные таблицы поездов туда и обратно, молча опираясь на
догадку о времени окончания концерта — ей же потом фильтрует обратные рейсы — и только в
последней фразе, уже под готовыми таблицами, предлагает уточнить время. Цены и номера поездов
в таблицах настоящие: `check_groundedness` подтвердил бы каждое число, потому что оно честно
взято из `tool_result`. Проблема не в том, что ответ опирается на непроверенные данные, а в том,
что часть входа сервер вообще не выдавал — время окончания концерта агент придумал сам и **этим
придуманным значением отфильтровал реальные данные**.

Это отдельный класс ошибки от двух, которые обычно разбирают: не «агент неправильно распорядился
данными, которые получил» и не «сервер не вернул данные, без которых нельзя обойтись» — а
«данных не было ни у кого, и агент молча заполнил пробел». Groundedness-проверка на выходе его не
ловит в принципе, потому что проверяет числа в ответе, а не происхождение фильтров, которыми эти
числа получены.

Отсюда премис-гейт (`tutu_mcp/premises.py`): значение, которое **сужает поиск** (фильтрует,
выбирает дату/направление/рейс), обязано прийти от пользователя или из предыдущего
`tool_result` — третьего источника нет. Вызов с придуманным значением возвращает
`clarification_required` вместо данных, до того как на нём построится таблица.

## Замеры каталога инструментов

Таблица ниже — снимок живого сервера на дату в шапке файла, вручную, не воспроизводится офлайн
(это чужая сериализация на проводе, у нас нет способа получить те же байты, не спросив сервер
ещё раз). Разбивка по слоям каталога (откуда байты и сколько срезалось) — величина другого рода:
она не про то, что ответил Туту в конкретный момент, а про то, что делает наш код с любым
каталогом, поэтому у неё есть воспроизводимый источник — `uv run python tutu.py measure`,
пересчитывает по записанной фикстуре `fixtures/_meta/tools_list.json`, закреплено
`tests/test_measure.py`. Цифры ниже это его вывод, а не живой замер, поэтому они не совпадают с
108 539/78 334 из README/доки байт-в-байт: другая сериализация (`json.dumps` вместо чужого
провода), тот же порядок величины.

| Что                                        | Значение                                                                 |
|---------------------------------------------|---------------------------------------------------------------------------|
| Инструментов на сервере                      | 16                                                                         |
| `tools/list` целиком (живой замер)           | 108 539 байт ≈ 30K токенов                                                |
| `search_rail` — только `description`         | 9 197 символов                                                            |
| `create_checkout_link`                       | 22 277 байт, ~50 параметров                                               |
| Плейбук `get_rail_instructions`              | 26 209 байт ≈ 7.5K токенов                                                |
| Ответ `search_rail` (10 офферов, compact)    | 26 338 байт ≈ 7.4K токенов, 3.4 с                                         |
| Дубли внутри одного оффера                   | `legs` / `checkout_ref` / `details_ref` / `review_summary` ≈ 60% объёма   |

Разбивка по слоям каталога (`tutu.py measure`, по фикстуре): top-level `description` — 44,7 КБ на
все 16 тулов, из них у трёх сжатых здесь (`search_rail`, `get_rail_seatmap`, `search_hotels`) —
32,5 → 16,2 КБ; проза внутри `inputSchema.properties[].description` — 31,4 КБ, сжимается до
15,6 КБ. После переноса именно этой прозы в результаты вызова парных `get_<domain>_instructions`:
`tools/list` 110 164 → 79 411 байт (**27.9%**), а с учётом `initialize`-инструкций сервера —
**33.1%** (прокси отдаёт свой блок инструкций на 1,9 КБ вместо 11,2 КБ у Туту). Обе цифры — уже с
учётом двух добавленных прокси тулов (`assess_request`, `check_groundedness`).

## Результаты эвалов

Четыре прогона по 22 сценария × 2 варианта, `gpt-5.6-luna` с `--effort low`, 19–21.08.2026.
Один из них — против живого `mcp.tutu.ru`, остальные по фикстурам; цифры совпадают в пределах
разброса модели. Полные трейсы — в отчётах `out/*.json` и трейс-вьювере.

| Метрика                          | baseline    | proxy                       |
|----------------------------------|-------------|-----------------------------|
| Поверхность инструментов, токены | 25 269      | 15 364 (**−39 %**)          |
| Задачный успех                   | 17–18 / 22  | 19–21 / 22                  |
| Обоснованность утверждений       | 97–98 %     | 99 %                        |
| Входных токенов за прогон        | 3,3–4,4 млн | на 0,43–0,67 млн меньше     |
| Гейт предпосылок сработал        | 0           | 8–12                        |
| Лишних уточняющих вопросов       | 0           | 0                           |

Экономия поверхности не зависит от прогона — это статическая цена каждой сессии до первого
поиска. Всё остальное — поведение модели, поэтому диапазон, а не одно число.

Прокси делает **больше** вызовов инструментов (гейт возвращает вопрос вместо данных, агент
повторяет вызов) и при этом тратит **меньше** входных токенов: сжатая поверхность окупает лишние
круги с запасом.

### Что известно про границы метода

- **Арифметика над подтверждёнными числами.** Ответ «поезд дороже автобуса на 575 ₽» (2 275,07 −
  1 700) проверку не проходит: обе половины из payload, само число — нет. Отличить её от неверной
  арифметики (умножить `stay_total` отеля на число ночей) детерминированная проверка не может, и
  ослаблять её ради этого нельзя — на умножении построен отдельный сценарий.
- **Промахи фикстур.** Модель каждый прогон просит чуть другие аргументы, поэтому даже после трёх
  проходов записи остаётся 0–6 промахов. Они считаются отдельной колонкой и не смешиваются с
  ошибками сервера.
- **Разброс между прогонами.** На одном и том же наборе `proxy` давал от 19 до 21 из 22. Сравнивать
  варианты имеет смысл только внутри одного прогона — они идут на одном бэкенде и одних фикстурах.

## Прочие наблюдения по серверу

- Ответ приходит только как `content[0].text` со строкой JSON, `structuredContent` не заполнен.
- Резолвинг сущностей («Питер» / «Мск», омонимы через `also_named[]`) на сервере уже сделан.
- Пагинация в основном закрыта: есть `meta.has_more`, `meta.total_matched`,
  `meta.post_filter_dropped_*`, фильтры применяются до пагинации.
- Относительные даты («через две недели») сервер не резолвит — не закрыто.
- Ленивая загрузка тулов через `find_tools` даёт 11 702 байта (89%) в теории, но после подгрузки
  rail-домена каталог снова 58 КБ (46%) — выигрыш не итоговый, а перенесённый; клиент, не
  обрабатывающий `notifications/tools/list_changed`, вообще не увидит тулов поиска. Замерено,
  не реализовано.
- Дедуп схем через `$defs`/`$ref` в `create_checkout_link` не даёт эффекта: повторяющихся
  под-схем на 0 байт, а между разными тулами `$ref` невозможен — каждый `inputSchema`
  самостоятелен.
